# QOC Analysis: Розподіл обов'язків при реєстрації видачі книги

## Question (Питання)
Хто та яким чином повинен відповідати за валідацію лімітів, розрахунок застави/сервісного збору та створення запису видачі книги (LoanRecord)?

## Options (Альтернативні варіанти)
* **Option A:** Залишити розрахунки та створення об'єктів у консольному методі `LegacyLibraryProcessor.issueBookFromConsole()` (поточний стан).
* **Option B:** Винести розрахунок фінансових показників у доменну сутність `LoanRecord`, а перевірки та логування винести у окремий доменний сервіс `LibraryIssueService`.
* **Option C:** Побудувати Rich Domain Model, де `LoanRecord` конструюється фабричним методом (Creator/Information Expert), розрахунок умов застави делегується поліморфним стратегіям розрахунку за категоріями книг (Polymorphism / Protected Variations), а координація виконується тонким Application Controller за участю штучних абстракцій (Pure Fabrication / Indirection) для логування та email.

## Criteria (Критерії оцінки за GRASP)
1. **Information Expert & Creator:** Об'єкт, що володіє даними книги та видачі, повинен сам розраховувати підсумкові суми та створюватися у валідному стані.
2. **Polymorphism / Protected Variations:** Зміна або додавання категорій книг не повинна викликати каскадну модифікацію `if-else`.
3. **Low Coupling & High Cohesion:** Консольний шар UI не повинен залежати від бізнес-правил розрахунку фінансів, логування чи відправки email.
4. **Pure Fabrication:** Інфраструктурні завдання (Audit Log, Email) повинні бути винесені в окремі технічні класи.

## Conclusion (Рішення)
**Обрано Option C.**
Option A порушує всі принципи GRASP, перетворюючи клас на God Object. Option B покращує стан, але залишає процедурне розгалуження. Option C забезпечує найвищий рівень High Cohesion, низьке зачеплення (Low Coupling ≤ 4) та гнучкість до розширення нових категорій книг.
